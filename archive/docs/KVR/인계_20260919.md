## 🚨 0. 이 세션에서 가장 중요한 교훈 — 축을 잘못 골랐다

**같은 실수를 반복하지 않으려면 이 절을 먼저 읽을 것.**

### 문제 정의
> "뉴비 태거가 바닥 로드아웃(굴리기 3종)으로 유저 5~6명을 못 잡는다"

### 내가 당긴 손잡이 — `GLOBAL_COOLDOWN` 2.0 → 1.5 → 1.0

🔴 **쿨은 숙련도에 비례해 효과가 커지는 축이다.** 빠른 쿨은 조준·판단이 좋은 사람이 더 잘 쓴다.
목적이 "격차 좁히기"인데 **"격차를 벌리는 손잡이"** 를 당긴 셈이다.

### 실측이 말한 것

```
GLOBAL 2.0 / 홀드 1.5    1단계 9·1·3·0 (3.25)    킹 2 · 러너 2   ← 50/50
GLOBAL 1.5 / 홀드 1.5    1단계 9·3     (6.0)     킹 2 · 러너 0
GLOBAL 1.0 / 홀드 1.5    1단계 7·9     (8.0)     (⚠️ 1단계 과함 ×2)
GLOBAL 1.5 / 홀드 2.0    1단계 4·8     (6.0)     킹 2 · 러너 0
GLOBAL 2.0 / 홀드 2.0    1단계 3·9·1·2·4 (3.8)   킹 3 · 러너 2   ← 원복 후
```

🔴 **쿨을 1.5로 내린 뒤 제작자(숙련자) 기준 4연승.** 2단계가 껍데기가 됐다(진입 2명 / 킹 피해 20 / 13초 종료).

### 판별 방법에 대한 교훈

```
1단계 처치 수   1.5에서 9·3·4·8 → 평균 6.0. 편차가 목표값(5.0)만큼 커서 2~4판으로 판별 불가
승률           2.0: 2승2패 → 1.5: 4승0패. 즉시 드러남
```
⚠️ **승률이 처치 수보다 빨리 신호를 준다.** 다음에 밸런스를 만질 때 이 순서로 볼 것.

### 대신 무엇을 했나
러너 구제를 줄이는 쪽(`REVIVE_DURATION` 1.5 → 2)으로 옮겼다. 부활 완료가 **판당 4건 → 2건**.
그 축은 조준 실력과 무관하게 모두에게 균등히 걸린다.
⚠️ **"홀드가 실력에 덜 민감하다"는 추론이지 측정은 아니다.**

### 🔴 이 축은 봇전으로 닫히지 않는다
진짜 뉴비 태거의 퍼포먼스는 **라이브에서만** 나온다. 제작자 플레이는 최적에 가깝고 봇전엔 뉴비가 없다.
**라이브 전에 붙일 것:** `📋 [RoundSummary] 1단계 처치` 와 `📡 [Telemetry] 승자` 를
**플레이 횟수 구간별**로 집계. 그것만이 뉴비/숙련자 격차를 보여준다.

## 2. 신규 기능

### 2-1. 봇 부활 시스템 (`ReviveSystem` + `RunnerBotDriveController`)

**ReviveSystem 공개 API**
```lua
ReviveSystem.beginReviveByCharacter(reviverChar, target)  -- target 생략 시 가장 가까운 다운자
ReviveSystem.isReviving(char)
ReviveSystem.cancelByReviver(char)
```
- `beginRevive(reviverChar, wantTarget)` 로 리팩터. **유저 경로(`startRevive`)는 인자를 안 넘겨 동작 불변.**
- 🔴 대상을 안 넘기면 ReviveSystem 이 '제일 가까운 다운자'를 **다시 고른다.** 봇이 한 검사가 무의미해지므로 반드시 넘길 것.

**봇 쪽 상수 (`RunnerBotDriveController`)**
```
BOT_REVIVE            = true    마스터 스위치
REVIVE_SEEK_RADIUS    = 35
REVIVE_START_DIST     = 8       ⚠️ 3D 거리다 (아래 3-2 참조)
REVIVE_CLAIM_TTL      = 7
REVIVE_BLOCK          = 6
REVIVE_KING_START     = 28      대상 선택 시 킹 거리
REVIVE_KING_CANCEL    = 20      진행 중 취소
REVIVE_FIRE_START     = 25      불벽 여유 (= 불벽속도 10 × 홀드 2초 + 5)
REVIVE_FIRE_CANCEL    = 8
REVIVE_FIRE_STALE     = 1.0
REVIVE_MAX_CONCURRENT = 2
REVIVE_SLOT_TTL       = 0.5
```

**부활 가드 3종** — 대상 선택 시 + 접근 중 매 틱 재검사
1. 킹이 그 자리 근처 (28 / 진행 중 20)
2. 불벽 뒤 (25 / 진행 중 8)
3. 위험 지대 안 (빙판·웅덩이 등, `dangerZones` 재사용)

### 2-2. `_G.FireLine` (`FirePressureSystem`)
```lua
_G.FireLine = { x = currentX, at = os.clock() }
```
- 불벽은 **X 한 좌표의 선**이다. 러너는 START(-222) → GOAL(784) 로 +X 이동하고 불은 뒤에서 쫓아온다.
  → **X 가 이 값보다 작으면 죽는 자리.**
- ⚠️ `BotDangerZone` 속성을 **일부러 안 붙였다.** 붙이면 봇의 일반 회피가 반응하는데, lane 탈출은 좌우로 빠지는 규칙이라 맵 폭 전체를 덮는 벽에선 무의미하고 "불벽이 앞으로 밀어낸다"는 압박 설계가 깨진다.
- ⚠️ `at` 시각을 실어 **끄는 코드가 필요 없다.** 라운드 종료·루프 중단 어느 경로로 끝나도 1초 뒤 만료.

## 3. 버그 수정

### 3-1. 배럴 자세 틀어짐 — ✅ 완전 해결
**증상:** 소환 시 배럴이 옆으로 기울어짐. `자세 0.89 ⚠️ 틀어짐` 로그.

**원인:** 자세(`CFrame.fromMatrix`)와 속도 사이에 `wait(0.05)` 가 있었다. 그동안 배럴은 **각속도 없이** 자유낙하 — 원통은 각운동량이 없으면 자세가 안 잡힌다.

**수정:** 속도·각속도를 `newItem.Parent = workspace` **직후**로 이동.
- ⚠️ CFrame 설정부(1694행)가 아닌 이유: 거기선 Parent 가 nil 이라 어셈블리가 물리 세계에 없다.
- ⚠️ 아래 `wait(0.05)` 블록의 배럴 분기는 **비워뒀다.** 여기에 속도를 다시 넣으면 08-26 의 "두 자리가 싸우는" 문제 재발.

**결과:** 이후 배럴 17발 전부 `자세 1.00 (즉시)`. 편차 0.

### 3-2. 봇 부활 거리 판정 — ✅ 해결
**증상:** `부활 시작 거절: 거리 초과 (12m) (x12)` 가 초당 수십 번.

**원인:** 내가 넣은 `REVIVE_START_DIST 8` 을 **XZ 평면**으로 쟀는데, `ReviveSystem.validateRevive` 는 `REVIVE_DISTANCE 10` 을 **3D**로 본다. 맵 Y가 121~137로 출렁여 경사·계단에선 XZ 8이어도 3D는 12~14.

**수정:** 판정은 3D, 이동 방향만 XZ. 높이로 끊긴 자리(XZ < 1.0인데 3D > 8)면 포기 타이머(7초) 안 기다리고 즉시 포기.

### 3-3. 해머하이 경고원 위치 — ✅ 해결
**증상:** 경고원이 태거 머리 위에 떠 보여 "범위가 실제와 다르다".

**원인:** `landingPosForTarget` 의 지면 레이캐스트가 **시전자만** 제외(`{ Char }`). 착지 후보 지점 +50 에서 아래로 쏘는데 그 자리에 태거가 있으면 **머리에 먼저 맞아** groundY 가 머리 높이가 된다. 해머하이는 태거를 조준하는 스킬이라 거의 매번 걸리는 조건.

**수정:** `Humanoid` 보유 최상위 Model 전부 제외. (이름 목록이 아니라 속성 판정 — 새 봇·NPC 자동 커버)

```lua
local ignore = { Char }
for _, m in ipairs(workspace:GetChildren()) do
    if m:IsA("Model") and m:FindFirstChildOfClass("Humanoid") then
        table.insert(ignore, m)
    end
end
```

- **비용 실측:** `GetChildren()` 은 재귀 아님(최상위 41개). 순회 1회 0.0217ms, 슬램당 2회 = 프레임 예산의 **0.26%**. 바로 아래 `doSlamHit` 이 매번 `GetDescendants()` 를 도는 것에 비하면 반올림 오차.
- **콜리전 그룹 기각 근거 (실측):** 캐릭터 HRP/Head = `Default`, 맵 충돌파트도 `Default` 가 2682개(89%). 그룹으로 캐릭터를 빼면 **지면도 같이 빠진다.**

🔴 **판정은 원래 멀쩡했다.** `doSlamHit` 은 XZ 평면 거리만 본다(Y를 0으로 누름) → groundY 가 틀려도 누가 맞는지는 안 바뀌었다. **순수 표시 버그.**
⚠️ **그러므로 `doSlamHit` 에 높이 제한을 넣으면 안 된다.** 넣으면 '떠 있는 원'을 기준으로 판정하게 되어 없던 불일치가 생긴다. (세션 중 내가 이 수정을 제안했다가 기각된 건이다)

### 3-4. 텔레메트리 오염 — ✅ 해결
`📡 [Telemetry] 부활 N회` 는 **"유저가 부활을 얼마나 쓰는가"** 를 재는 값이었는데, 봇 부활 도입으로 봇↔봇이 섞였다.
> 실측: 유저가 태거였고 부활을 한 번도 안 한 판에서 **"부활 7회"** 가 찍혔다.

**수정:** `reviverPlayer` 를 텔레메트리 위로 올려 **살린 쪽이 플레이어일 때만** 집계.
⚠️ 살려진 쪽(target)은 안 본다 — 그 구분은 코인 보상이 `targetIsPlayer` 로 이미 하고 있다.

## 6. 미결

### 6-1. 🔴 `RevivalFlag.REVIVE_DELAY` — 관계가 깨진 상태
`RunnerItem.RevivalFlag.Server` 주석:
> *"[3 의 근거] 일반 부활(`ReviveSystem.REVIVE_DURATION`)이 **1.5초 홀드**다. 광역 자동이라는 이점의 대가로 **그 2배**를 지연으로 준다."*
> *"⚠️ ReviveSystem 의 홀드 시간을 바꾸면 **여기도 같이 볼 것**(2배 관계 유지)."*

```
REVIVE_DELAY = 3     ← 홀드가 2초가 됐으므로 2배 관계를 지키려면 4
```
⚠️ **의도적으로 안 건드렸다.** 깃발은 러너 아이템이고 3→4는 별도 밸런스 판단이다(다운 10초 중 4초 대기). 홀드 2.0과 같이 넣으면 러너 구제가 두 곳에서 동시에 약해져 효과를 못 가른다.

### 6-2. 스톤이 태거베이스를 관통 — 미해결, 원인 미확정
**제보 1회 (수십 판 중 처음). 재현 안 됨.**

**확인된 사실:** `lift` 는 시작 배율(0.75)만 본다 → 9.5. 그런데 스톤은 2.5초에 걸쳐 `STONE_MAX_SCALE 2.20` 까지 자라 반지름이 22가 되고, 성장 루프는 **Size 만** 바꾸고 CFrame 은 안 건드린다.

🔴 **이게 원인인지는 모른다 — 단정하지 말 것:**
- 돌은 굴러간다. 다 자랄 때쯤 스폰 지점에 없고 물리가 내내 접촉을 푼다
- 0.1초당 반지름 증가가 0.58 stud 뿐이라 한 번에 깊이 파고들 구조가 아니다
- 태거베이스가 얇은 슬래브인지 확인 안 함
- "베이스 아래에서 스폰"이 어떻게 가능했는지 설명 못 함

**재현되면 찍을 것:** 관통 순간의 ① 돌 중심 Y ② 아랫면 Y ③ 바닥 파트 두께. 이 세 줄이면 갈린다.
(코드에 같은 내용의 주석을 남겨뒀다 — `ItemSpawnHandler` stone lift 계산부)

### 6-3. Spear 가 사실상 무쓸모

### 왜 안 지워도 되나 — DevAuth 가 전면적으로 걸려 있다

```
DevAuth 모듈 (공유 화이트리스트)   →  13개 스크립트가 require
인라인 동일 게이트                 →   9개 스크립트
```

DevAuth 자체가 **fail-closed** 로 설계돼 있다 — *"실패 시 isDev 가 false면 커맨드 차단."*

가장 위험했던 항목(`GroupRewardSystem:194`, 주석에 *"코인 300 을 반복 지급할 수 있다"*)을 직접 읽었다:

