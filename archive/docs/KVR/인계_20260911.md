## 1. 이번 세션에 실제로 바꾼 코드

### 1-1. `RunnerBotDriveController` — botAngle 신규 (버그수정, 검증 완료)

**증상:** 강타 한 방에 봇 10~11마리 전원이 걸린다. `PushTool.Server:209` 에 실측으로 기록돼 있던 그 문제.

**원인:** 봇 산개 각도를 이름 해시로 뽑았는데,

```lua
h = (h * 31 + bot.Name:byte(i)) % 360
```

봇 이름이 `AIRunner_1` ~ `AIRunner_11` (`RoundSystem:663`) 로 **접두사가 전부 같다.** 마지막 글자만 다르면 해시도 그 바이트 차이(1)만큼만 달라진다. 실측 각도:

```
AIRunner_1~9  → 346, 347, 348, 349, 350, 351, 352, 353, 354
AIRunner_10,11 → 334, 335
총 스팬 20°  ·  최소간격 1°  ·  r=4.8 에서 호 길이 1.68 stud
```

**11마리가 1.68 stud 안에 겹쳐 선다 = 산개가 아니라 한 점.** 09-09 링 분산 수정도, 그 전 존 분산도 같은 이유로 **처음부터 no-op 였다.** 히트박스 10³→7³ 축소가 효과 0이었던 것도 이걸로 설명된다 — 한 점에 모여 있으면 박스를 줄여도 다 걸린다.

**수정:** `GOLDEN_ANGLE = 137.5` + `botAngle(bot)` 헬퍼를 만들고 두 곳을 통일.

```lua
local GOLDEN_ANGLE = 137.5
local function botAngle(bot)
    local idx = bot:GetAttribute("BotIndex")
    if not idx then
        local h = 0
        for i = 1, #bot.Name do h = (h * 31 + bot.Name:byte(i)) % 360 end
        idx = h
    end
    return math.rad((idx * GOLDEN_ANGLE) % 360)
end
```

적용 지점 (편집으로 줄번호가 밀렸으니 심볼로 찾을 것):
- `botAngle` 정의 — `ZONE_SPREAD_RATIO` 바로 아래
- `zoneOffset(bot, zone)` — 내부 인라인 해시 제거, `botAngle(bot)` 호출 (1·2단계 존 분산)
- 링 분기 (`elseif tRoot then` 폴백, `ringR = ATTACK_RANGE * 0.8` 바로 아래) — 인라인 해시 제거

결과 각도: `20, 52, 72, 105, 138, 158, 190, 242, 275, 295, 328` — 최소간격 20°.

**되돌리려면** `botAngle` 이 `math.rad(h)` 를 그대로 반환하게 한다.

⚠️ `:1068` 의 좌/우 회피 해시(`% 2`)도 같은 패턴이라 검산했는데 시퀀스 `0,1,0,1,0,1,0,1,0,0,1`(좌 6·우 5)로 **우연히 멀쩡하다.** 건드리지 말 것.

### 1-2. `RunnerBotDriveController` — KILL_ROUND_CHANCE 0.35 → 0

**왜:** 킬 모드가 더 약한 모드다(아래 2-3 참조). 35% 확률로 약한 모드가 걸리면 "판별 난이도 리듬"이 아니라 **3판에 1판이 헐거운 판**이다. 솔로모드 긴장감 목표와 정면 충돌.

**왜 트리거를 안 만들었나** — "점령이 막히면 킬로 전환"을 설계했다가 폐기:
1. 그 반응 로직이 **이미 점령 분기 안에 있다.** 킹이 `ZONE_HOLD_RADIUS` 안이면 봇이 직접 붙어서 때리고, 밖이면 존을 민다. 어느 쪽이든 킹이 압박받는다. 킬 모드가 더해 주는 건 '목표 압박을 없애는 것' 뿐.
2. **더 약한 모드로 가는 일방 전환은 악용된다.** 킹이 일부러 존을 틀어막아 전환을 유발하면 더 쉬운 판을 얻는다 — 벌하려던 행동에 상을 주는 꼴.

**대가:** 판별 다양성이 0이 된다. 그 역할은 **히어로봇 수(0~3 랜덤)** 로 옮긴다 — 무기가 눈에 보여 킹이 판 시작에 읽을 수 있고, 어느 조합이든 압박이 안 죽는다.

`_G.RunnerBotsGoKill`(왕좌 붕괴)은 **그대로 둔다.** 존이 실제로 사라진 경우라 "약한 모드로 도망"이 성립하지 않는다.

⚠️ 부작용: 링 분기가 이제 왕좌 붕괴 후에만 돈다. 링 쪽을 테스트하려면 `/botmode kill` 강제가 필수.

## 2. 실측으로 확정된 것 (이제 단정해도 되는 사실)

### 2-1. SPLIT 모델 — 전 구간 일치

```lua
swingSplitRaw = math.max(1, weighted)          -- 가중 인원
swingSplit    = math.min(swingSplitRaw, SPLIT_CAP)   -- ⚠️ 캡은 n 에 걸린다 (분모가 아님)
dmg           = dmg / (swingSplit ^ SPLIT_EXP)
```

`SPLIT_EXP = 0.5`, `SPLIT_CAP = 2.5`, `BOT_SPLIT_WEIGHT = 0.25`, `BOT_KING_SPLIT_WEIGHT = 0.10`

3판 로그의 splitTag 를 전부 역산해서 소수점까지 일치 확인:

```
×1.8 (봇 7)  7×0.25=1.75  40/√1.75 = 30.2  ✓
×1.5 (봇 6)  1.50         40/√1.50 = 32.7  ✓
×1.2 (봇 5)  1.25         40/√1.25 = 35.8  ✓
×2.2 (봇 9)  2.25          7/√2.25 =  4.7  ✓ (슬랩)
×2.0 (봇 8)  2.00          7/√2.00 =  4.9  ✓ (슬랩)
×1.0 (봇 ≤4) max(1,·)=1.0  40/1     = 40.0 ✓
```

**유저 기준 실제 표:** 1명 40.0 / 2명 28.3 / **3명 이상 25.3 (평평)**
**봇 기준:** 4마리↓ 40.0 / 5마리 35.8 / 6마리 32.7 / 8마리 28.3 / 10마리 25.3

⚠️ **분산 수정 후 SPLIT_CAP(2.5)은 봇전에서 한 번도 안 걸렸다** (3판 최대 2.25 = 봇 9마리). 봇전에서는 사실상 사문화된 값.

⚠️ **봇전 측정은 분산 효과를 과소평가한다.** 봇 9마리 = 2.25명분이지만 유저 9명이면 상한에 걸려 25.3이다. 실전 로비 숫자는 이 로그와 다르다.

### 2-2. 분모는 스윙 단위가 아니라 '히트 검사 패스' 단위다

`performHitCheck` 가 `HIT_WINDOW` 동안 `HIT_CHECK_RATE` 간격으로 반복 호출되고, **패스마다 `swingSplit` 을 새로 뽑는다.** `hitVictims` 가 중복만 막는다.

실측 (스윙 1회가 5명 명중):
```
47.146  AIRunner_7   ×1.0명   ┐ 패스 A = 4명 (1.0)
47.148  AIRunner_10  ×1.0명   │
47.149  AIRunner_5   ×1.0명   │
47.150  AIRunner_3   ×1.0명   ┘
47.371  AIRunner_8   ×1.0명   ← 패스 B = 1명 (1.0), 221ms 뒤
```

**시간차로 박스에 들어오면 분산 페널티를 아예 안 문다.** 결과적으로 공간 분산이 시간 분산을 만들고, 시간 분산이 감쇠를 무력화한다:

| | 명중 | 1인당 | 스윙 총딜 |
|---|---|---|---|
| 수정 전 | 10명 (1패스) | 25.3 | 253 |
| 수정 후 (1패스) | 6명 | 32.7 | 196 |
| 수정 후 (2패스) | 6명 | **40.0** | 240 |

명중은 줄었는데 1인당이 25.3 → 40.0(+58%)이라 총딜은 거의 그대로. **코드 어디에도 안 적혀 있던 동작.** 스윙 단위로 묶을지는 미결(우선순위 낮음).

### 2-3. 킬 모드가 약한 메커니즘 = 초당 타격 횟수

지금까지 DPS 격차로만 알던 것의 원인이 잡혔다.

| 판 | 타격 | 2단계 | 초당 |
|---|---|---|---|
| 점령 | 61회 | 43.5s | **1.40** |
| 킬 A | 39회 | 41.5s | 0.94 |
| 킬 B | 37회 | 50.8s | 0.73 |
| 킬 C | 31회 | 34.9s | 0.89 |

**킬 모드는 초당 타격이 약 39% 적다.** 데미지 계수가 아니라 봇이 사거리 안에 있는 시간이 줄어든 것. 킹이 움직이면 링 목표점도 같이 움직여 봇이 계속 이동 중이고, 그 시간이 손실.

**점령은 킹을 묶고, 킬은 킹을 푼다.** 존이 차오르면 킹은 막으러 와야 하지만 킬 판은 킹이 어디에 있을 의무가 없다.

그리고 K는 반대로 좋아진다 (킬 3.2~4.8s vs 점령 6.1s) = **킬 모드는 봇이 킹에게 먹이를 갖다 바치는 구조.**

### 2-5. 링 반경이 병목 — 존 분산보다 나쁘다

강타 명중 인원:
```
점령 모드 (존 분산)   6 / 5 / 6
킬 모드   (링 분산)   8/6/6/1/1 · 5/9/5/1/1 · 6/9/6/3
```

```
zoneOffset  r = min(존X, 존Z) × 0.5 × ZONE_SPREAD_RATIO(0.55)  → 존 40이면 ≈11
ring        r = ATTACK_RANGE × 0.8                              → 4.8
```

**강타 박스 반폭이 5인데 링 최대 |X| 가 4.8** 이라 옆으로 빠지는 게 물리적으로 불가능하고, 후방 호(약 36%)로만 탈출된다. 평균 6.5명 명중은 그 36%와 정확히 맞는 값. **각도 수정은 제 몫을 다했고 남은 건 기하 한계.**

**ringR 을 올리지 않기로 결정.** 이유:
- 정지 허용치가 2 stud 라 r=5.5 면 실제 위치가 3.5~7.5 로 흩어진다 → 사거리 6 밖 봇이 생겨 이미 39% 부족한 초당 타격이 더 떨어진다. 약한 모드를 더 약하게 만든다.
- `KILL_ROUND_CHANCE = 0` 이라 링 분기는 왕좌 붕괴 후 몇 초만 돈다. 실전 경로는 존 분기고 거기는 r≈11 로 이미 충분히 흩어진다. **안 쓰는 경로 최적화.**

## 3. 로그 판독 함정 (반복해서 속았음)

### 3-1. `📈 [Capture] ... 킹 없음` 은 킹의 부재를 뜻하지 않는다

`CaptureSystem:693` 의 print 는 관문이 셋이다:
```lua
if z.runners > 0 then          -- 러너 있어야
  if zoneProgress[i] > pk then -- 최고점 새로 갱신해야
    if after > before then     -- 25% 선 새로 넘어야
      print(... 킹 있음/없음 ...)
```

**킹이 존에 있으면 rate 가 4~20배 느려지거나 음수라서 최고점 갱신이 안 일어나고, print 자체가 안 나간다.** 러너 1명 상황에서는 rate 가 음수(−0.039)라 "킹 있음"이 찍히는 게 수학적으로 불가능하다.

→ **이 로그는 "킹 없음"만 찍히도록 구조적으로 편향돼 있다.** 게이지가 오를 때만 찍히고, 게이지는 킹이 없을 때 오른다.

**대신 봐야 할 것: 거리 필드.** 주석의 읽는 법 — `거리 100+` = 못 온 것(이속·경로), `거리 20~50 유지` = 문 앞에서 밀려나는 것. 09-10 실측은 30/35/16/42/48/25 로 **전부 16~48** = 킹이 매 시점 존 코앞에 있었다.

⚠️ `CaptureSystem:683` 주석에 이 오독 사례가 **이미 기록돼 있다**(09-03, 6건 전부 "킹 없음"을 해머 스핀 밀어내기로 오독). 그 경고 열 줄 아래의 print 를 읽으면서 같은 실수를 반복했다.

### 3-2. `[Duel] 킹 피격` 은 봇 킹 전용

`TaggerBotSystem` 의 `bHum` 핸들러라 **유저가 킹인 판에서는 구조적으로 0줄.** 그 부재를 '피해 0'으로 세 번 오독한 이력이 있어서 `Stage2TriggerSystem.watchKingDamage` 를 따로 세웠다.

### 3-3. `🐢 [Lag] 프레임 히치` 폭주는 프로브 고장이 아니다

`HITCH_MS = 50` 인데 스튜디오가 15fps(=66ms/프레임)면 **모든 프레임이 임계를 넘어 초당 15줄**이 나간다. 스튜디오가 느린 게 그대로 찍힌 것. 그리고 프로브 자신이 프레임을 갉아먹어 측정을 오염시킨다(`_LagProbeClient:15` 주석이 경고).

### 3-4. 주석은 changelog 스택이다 — 현재 상태 표가 아니다

`PushTool.Server` 의 `3명 23.1 / 5명 23.1 / 8명 23.1` 같은 줄들은 **각각 다른 날짜의 변경 기록**이고 그 날짜 기준으로는 정확하다. 이걸 하나의 현재 표로 뭉개면 현재 값과 안 맞는다. **코드에서 계산할 것, 주석 표에서 계산하지 말 것.**

## 4. 미결 항목 (우선순위 순)

### 4-1. 계측 2배 수정 — 진단 대기 (즉시 가능)

09-04 에 `if d > hum.MaxHealth then d = hum.MaxHealth end` 클램프가 들어가서 "정확히 2배"(825→1650)는 사라졌지만 **완치가 아니었다.**

```
09-10 실측: 킹 사망 판 1890 / 61회 (HP 825)
61 × 20.0 = 1220  →  약 670 을 한 이벤트가 몰아넣었다
670 < 825 이므로 클램프를 그냥 통과한다
```

**670의 정체가 재산정 경합인지 사망 처리인지 미확정.** 처방이 다르다:
- 재산정 경합 → 재산정 2곳(유저 킹 / 봇 킹)에 `HpRewrite` 표식 + `task.defer` 해제
- 사망 처리 → 사망 이벤트(`h == 0`) 제외

**진단 코드가 이미 들어가 있다** (`watchKingDamage` 내 `if d > 100 then warn(...)`, 클램프 바로 위). 임계 100 인 이유: 실제 피격은 봇 평타 20.0 고정, 마법책 최대 36.7, 곡사포 최대 23.6 — 100 위는 전투 피해가 존재할 수 없는 구간.

**필요한 측정: 킹이 죽는 판 1판.**
```
1. /botmode random        (점령 모드가 초당 타격 1.40 으로 훨씬 세다)
2. 1단계 아이템 쓰지 말 것 (봇 10마리 유지)
3. 2단계에서 거의 안 싸운다 (30초쯤에 죽는다)
```
찍힌 시각을 `👑 [Stage2] 태거 HP 재산정` / `[Punch] -> death` 와 대조하면 확정. `HP0=true/false` 필드가 판별용.

### 4-2. 웨폰 DPS 재측정 (4번)

기준선이 이제 있다 — **킹 HP 825 · 봇 10 · 2단계 34.9~50.8s · 초당 타격 0.73~0.94(킬) / 1.40(점령).**

- 다른 무기도 DiamondBlade 처럼 MaxHealth 비례 계수를 쓰는지 grep 필요
- 09-09 의 등급별 DPS 목표는 폐기(사이드그레이드 결정) → 단일 밴드로

### 4-3. 히어로봇 설계 (5번) — 우선순위 올라감

`KILL_ROUND_CHANCE = 0` 으로 판별 다양성이 0이 됐고, **그 역할을 히어로봇이 대신 맡기로 했다.** 원래 4번 다음이었지만 공백을 메우는 역할이 생겨 중요도가 올라갔다.

확정된 방향:
- 히어로봇 수 0~3 랜덤 = 판별 다양성 (무기가 보여서 판 시작에 읽힌다)
- 나누려면 코인 말고 **역할로**: 히어로는 킹 추격, 농민은 점령. 화면에서 즉시 읽히고 "왜 저놈들이 나한테 오는지"가 설명된다
- 봇도 러너 웨폰을 들 수 있다 — 8종 중 7종이 서버 Script 에서 `Tool.Activated` 처리(ClassicSword 만 `FXClient` 경유). `PushTool.BotAction` 이 실전 검증된 선례
- 고정 h 로 (인원 비례 아님). `Dn_히어로 = Du × 봇 조작 효율`
- ⭐ 히어로봇의 차별점을 "무기 DPS"가 아니라 **"후방 호를 쓸 줄 아는 봇"** 으로 두는 안 — 데미지 수치를 안 건드리고도 농민봇과 체감이 갈리고, 러너가 배워야 할 행동이라 솔로모드 튜토리얼 목적과도 맞는다

**미결 결정 (유저):** 히어로 승격 시점(2단계 진입 vs 킹 HP 임계) / 솔로모드 전용 여부

### 4-4. 사이드그레이드 라벨 작업 (병렬 가능, 의존 없음)

**2.0 출시 전 러너 웨폰을 사이드그레이드로 변경 결정됨.** 근거: 라이벌(Rivals)은 사이드그레이드 + 희귀도는 코스메틱 전용, DbD 는 퍽 사이드그레이드 / 애드온은 등급제인데 일관성 실패. BHVR 의 "희귀할수록 이상해진다(강해지지 않는다)"는 이미 실패한 접근.

태거 아이템은 **등급 = 강함이 맞다**(통나무 굴리기 노말 vs 에너지볼 레전드는 우열이 명백). 러너 웨폰만 사이드그레이드.

작업 목록:
1. `UnifiedInvenClient` 웨폰 카드: 희귀도 라벨 → `WeaponData.short` 로 교체
2. `ShopSystem:129` `WEAPON_PRICE` 평탄화 (현재 Normal 1000 / Rare 2000 / Epic 3500 / Legendary 5000)
3. `WeaponData` 배열을 역할 순으로 재정렬 (현재 희귀도 순, 소비처 4곳)
4. `ClassicSword.short` "Balanced starter" → "starter" 제거
5. 09-09 문서 2-3 의 "등급 자리에 끼워 넣을 것" 주석 정정
6. ⚠️ `rarity` 필드는 **남긴다** (정렬·색상 참조용)

`WeaponData.short` 가 이미 역할 태그로 기능한다:
```
ClassicSword  "Balanced starter"      HammerLow    "Heavy spin"
DragonFire    "Stack and burn"        SakuraBlade  "Keep the tempo"
DiamondBlade  "Strike the marks"      HammerHigh   "Leap and slam"
KatanaSword2  "Counter the knockback" Gauntlet     "Charge and slam"
```

**미결:** 희귀도 라벨 처리 방식 — 태거 아이템에는 라벨이 붙어 있는데 웨폰에도 같은 라벨이 있으면 강함의 척도로 읽힌다. (Rivals 방식 = 라벨 유지하되 코스메틱 전용임을 UI 로 분리)

## 6. 다음 세션이 피해야 할 오류 패턴

이번 세션에 내가 실제로 반복한 실수들. 같은 함정이다.

1. **주석을 실측으로 인용** — 주석은 날짜별 changelog 스택이다. 각 항목은 그 날짜엔 맞았지만 현재 값이 아니다. `PushTool.Server` 캡 표를 현재 표로 읽어 수치를 세 번 틀렸다. **코드에서 계산할 것.**
2. **선택 편향된 로그를 전수로 읽음** — `📈 [Capture] 킹 없음` 6건을 "킹이 한 번도 안 왔다"로 읽었다. 그 print 는 킹이 없을 때만 발생 가능한 조건에서 찍힌다. **"이 로그가 반대 결과를 찍을 수 있는 구조인가"를 먼저 확인.**
3. **측정 프로토콜의 인공물을 설계 발견으로 읽음** — "킹이 존을 방치했다"는 내가 "강타를 그룹에 반복해서 꽂아라"라고 지시한 결과였다. **테스트 지시를 내렸으면 그 결과를 발견으로 세지 말 것.**
4. **비교 대상을 잘못 세움** — "뭉치면 팀에도 이득"이라고 했는데, 1인 팀과 N인 뭉침을 비교한 오류였다. 올바른 비교(N 산개 vs N 뭉침)로는 뭉치면 팀 HP 소모가 2.5배 빠르다.
5. **표본 1개에서 일반화** — 무기 1종 → 8종 전체, API 시그니처 1개 → 시스템 전체.

**공통 처방:** 단정 전에 "이걸 반증할 수 있는 관측이 이 로그에 존재하는가"를 묻는다. 존재하지 않으면 그건 측정이 아니라 가정이다.

## 7. 제작 원칙 (유지)

- 기술 소통은 전부 한국어 반말
- 지시/프롬프트는 항상 **하나로 합친 통합본**. 여러 개로 쪼개지 말 것
- 측정 전에 단정하지 않는다
- 한 번에 하나만 바꾸고 F5 로 확인한다 (`PushTool.Server:162` 에 "세 변경이 겹쳐 있으니 처치 수만 보고 판단하지 말 것" 경고 사례 있음)
- **제외 목록보다 결과 보장** — 무엇을 맞았나로 거르는 방식은 반드시 다시 깨진다. 결과를 보장하는 규칙으로 뒤집는다
- 정리 그물은 이름 목록이 아니라 **속성**으로 (`TaggerSpawnedItem`, `GroundRayIgnore`)
- `Accessory` 해제는 `Destroy` (`Parent = nil` 은 해제가 아니다)
- 월드에서 "안 보임"은 좌표부터 찍는다 (부착·복제는 같은 프레임에 안 끝나므로 `task.delay(0.3)` 뒤에 측정)
