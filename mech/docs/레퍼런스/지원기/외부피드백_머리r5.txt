두 파일을 함께 보면, 현재 머리는 **이미지의 윤곽을 복셀로 변환한 뒤 바이저와 마스크를 덧입히는 방식**으로 만들어져 있습니다. 단순히 복셀이 부족해서 엉성한 게 아니라, **2D 영역을 3D 표면에 투영하는 방식과 부품을 만드는 순서** 때문에 원본의 입체적인 장갑 구조가 일부 평면화된 것이 핵심입니다.

먼저 중요한 점부터 말씀드리면, 제가 이전에 제안한 **“바이저 높이를 20~30% 줄이자”는 조언은 수정하는 게 좋겠습니다.** 코드를 보면 이전 작업에서 이미 *넓은 띠 형태의 바이저*와 *귀 밑에서 턱을 감싸는 U자 마스크*를 의도하셨고, ×1.0에서는 바이저 본체가 높이 5복셀뿐입니다. 무턱대고 얇게 만들기보다 **하단의 뾰족한 형태와 주변 장갑의 깊이 관계를 조정하는 편**이 적절합니다.

## 1. 두 파일의 역할

### `apis_head_r4.py`: 머리 생성 코드

코드의 주요 흐름은 다음과 같습니다.

1. `apis_head_r3`에 정의된 정면·측면 윤곽을 가져옴
2. 두 윤곽의 교집합으로 머리 기본 덩어리를 만듦
3. 정면·측면 이미지 좌표에 정의한 다각형으로 색상과 부품 영역을 지정
4. 마스크를 돌출하고 중앙 턱판을 추가
5. 바이저 부분을 2복셀 파냄
6. 귀 원반과 목을 추가
7. 바이저를 별도 파트로 분리
8. 정면·측면·3/4 비교 이미지를 렌더링

즉, 직접 복셀을 하나씩 조각하는 방식이 아니라 **참조 이미지의 실루엣과 영역을 이용한 절차적 모델링**입니다.

### `APIS_head_r5_x1.0.json`: 생성된 머리 데이터

JSON에는 `Head`와 `Visor` 두 파트가 들어 있습니다.

| 항목 | 확인된 내용 |
|---|---|
| 포맷 | `flag_vox/1` |
| 복셀 크기 필드 | `0.05` — 실제 단위는 파일만으로 확정 불가 |
| Head | 22,553복셀 |
| Visor | 67복셀 |
| Head 전체 범위 | 31 × 34 × 41복셀 |
| Visor 범위 | 19 × 1 × 5복셀 |
| 연결 상태 | Head와 Visor 각각 6방향 기준 하나의 연결 덩어리 |
| 파트 겹침 | Head와 Visor 사이 같은 좌표의 중복 없음 |

Head 범위에는 아래쪽 **목까지 포함**됩니다. 따라서 41복셀을 얼굴 높이로 해석하면 안 됩니다.

또한 JSON의 `Head`는 부모를 `Torso`로 지정하지만, 이 JSON 자체에는 `Torso` 파트가 없습니다. 전체 몸체에 결합하는 맥락에서 저장된 머리 데이터로 보입니다.

> **버전 주의:** 파이썬 파일 이름과 상단 설명은 `r4`인데 코드 내부에는 `r5` 수정 주석이 있고, JSON은 `r5`입니다. 두 파일이 완전히 동일한 실행 결과인지 증명할 수는 없지만, 코드와 JSON에 나타난 형태는 서로 연관된 작업으로 분석할 수 있습니다.

# 2. 가장 큰 원인: 정면·측면 윤곽의 교집합

핵심 코드는 여기입니다.

```python
hull = fm[py, pxf] & sm[py, pxs]
```

쉽게 말하면:

- 정면 그림에서 머리 안에 들어가는 위치인지 확인
- 측면 그림에서도 머리 안에 들어가는 위치인지 확인
- **두 조건을 모두 만족하는 복셀만 채움**

이 방식은 큰 외곽을 빠르게 잡는 데는 좋습니다. 지금 모델이 정면과 측면 모두에서 메카 머리처럼 보이는 이유이기도 합니다.

하지만 한계도 분명합니다.

### 생기는 문제

정면 윤곽과 측면 윤곽만으로는 다음을 충분히 알 수 없습니다.

- 이마 중앙이 얼마나 앞으로 나오는지
- 노란 좌우 장갑이 가운데보다 얼마나 돌출되는지
- 바이저 양끝이 머리 옆으로 얼마나 감기는지
- 턱판 중앙과 측면의 깊이가 어떻게 다른지
- 위에서 봤을 때 머리가 어디서 좁아지는지

그 결과 기본 덩어리가 **정면 모양을 앞뒤로 늘린 형태와 측면 모양을 좌우로 늘린 형태의 교집합**이 됩니다. 현재 이미지에서 노란 헬멧이 하나의 큰 덩어리처럼 보이는 주요 구조적 이유입니다.

### 개선 방향

이 방식 자체를 버릴 필요는 없습니다. 다만 이를 **기본 내부 골격**으로만 쓰고, 주요 장갑은 별도 구조로 만드는 편이 좋습니다.

```text
기존 교집합 머리 = 내부 프레임

그 위에 별도로:
├─ 노란 상부 장갑
├─ 노란 좌우 관자놀이 장갑
├─ 흰색 이마판
├─ 어두운 바이저 테두리
├─ 청록색 바이저
└─ U자 마스크 + 중앙 턱판
```

이렇게 나누면 정면·측면의 참고 형태는 유지하면서도, 원본에서 중요한 **장갑의 겹침과 깊이 차이**를 조절할 수 있습니다.

# 3. 바이저: 왜 아래가 뾰족해 보이는가

이 부분은 JSON에서 실제 복셀 형태를 직접 확인할 수 있습니다.

별도 `Visor` 파트는 전부 같은 앞뒤 좌표 `y = -13`에 놓인 **한 복셀 두께의 평면**이고, 높이에 따른 가로 폭은 아래와 같습니다.

```text
위   z=234   ███████████████████   19칸
     z=233    █████████████████    17칸
     z=232     ███████████████     15칸
     z=231       ███████████       11칸
아래 z=230          █████           5칸
```

이 구조 때문에 빛을 꺼도 바이저의 아래쪽이 좁아지는 **역삼각형에 가까운 실루엣**이 나옵니다. 이전 이미지에서 웃는 입처럼 보였던 건 단순한 조명 문제만이 아니라 **실제 복셀의 외곽 형태에도 원인**이 있습니다.

### 다만 꼭 알아야 할 점

별도 `Visor` 파트 외에도 `Head`에 색상 번호 `6`인 복셀이 **71개** 있습니다. 이 번호는 코드에서 바이저와 귀의 청록색 등에 사용됩니다.

따라서 화면에 보이는 모든 청록색이 반드시 `Visor` 파트의 67개 복셀만은 아닙니다. 바이저를 수정할 때 `Visor`만 줄이거나 옮기면 주변 청록 복셀이 남아 **얼룩이나 끊어진 띠**처럼 보일 수 있습니다.

### 권장 수정

현재처럼 넓은 띠라는 의도는 유지하되, 하단 폭을 덜 급격하게 줄이는 게 좋겠습니다. 예를 들어 첫 시험안으로는:

```text
위       ███████████████████
         ███████████████████
         █████████████████
         ███████████████
아래      █████████████
```

이건 정확한 최종 설계도가 아니라 **형태 테스트용 제안**입니다. 현재의 `19 → 17 → 15 → 11 → 5`보다 아래쪽 중앙이 수평적으로 읽히도록 하는 게 목적입니다.

추가로:

- 바이저 둘레에 **1복셀 정도의 짙은 프레임**을 둘 수 있는지 검토
- 양끝은 바이저가 옆으로 감기는 느낌을 내되, 좌우를 과도하게 늘리지 않기
- `Visor`와 `Head`에 나뉜 청록색 복셀을 함께 점검하기

### 이전 조언에 대한 정정

제가 앞서 블룸이 강하다고 말했는데, **올려주신 코드만으로 블룸 설정을 확인할 수는 없습니다.** 렌더러 내부의 `vox_preview` 구현과 발광 설정이 없기 때문입니다. 이미지가 밝게 뭉쳐 보이는 것은 사실이지만, 원인이 블룸인지 발광 표현인지 후처리인지 단정할 수는 없습니다.

# 4. U자 마스크: 의도는 좋지만 표면 생성 방식이 복잡함

코드에서 마스크는 단순히 색만 칠한 것이 아니라, 정면 영역을 기준으로 돌출합니다.

```python
H.emboss(F("mask") & ~F("vis"), 8, h=2)
```

그리고 중앙 턱판은 각 위치의 가장 앞 복셀을 찾아서 추가로 앞으로 내밉니다.

```python
front_j = np.where(anyf, filled.argmax(1), -1)

for i, kz in np.argwhere(chin2 & anyf):
    j = front_j[i, kz]
    for d_ in (1, 2):
        if j - d_ >= 0:
            H.a[i, j - d_, kz] = 8
```

즉:

1. 기존 머리 표면을 바탕으로 마스크를 돌출
2. 그 위에서 다시 중앙 턱판을 돌출
3. 턱판 외곽에 어두운 테두리 추가

하는 구조입니다.

### 왜 복잡해 보일 수 있나

기존 머리의 앞면은 하나의 평평한 면이 아니라 복셀 계단입니다. 각 위치마다 가장 앞에 있는 복셀의 깊이 `front_j`가 다르면, 여기에 다시 돌출과 테두리가 적용되면서 **턱판의 깊이와 외곽선도 계단을 따라 움직입니다.**

그 결과로 생길 수 있는 현상은 다음과 같습니다.

- 턱판 테두리가 일정한 한 줄이 아니라 여러 깊이에서 보임
- 측면에서 수평 줄이 많아 보임
- 중앙 턱판보다 U자 마스크 전체가 하나의 주름진 덩어리로 읽힘

이미지에서 보이는 하부의 촘촘한 줄은 이 생성 방식과 관련이 있을 가능성이 있습니다. 다만 `H.emboss()`와 렌더러 구현을 아직 보지 못했기 때문에 이것만이 유일한 원인이라고 확정할 수는 없습니다.

### 중요한 점: 마스크 자체가 없는 것은 아닙니다

JSON에 마스크 색으로 사용되는 `8번` 복셀은 **1,091개** 있습니다. 이전에 제가 이미지 인상만 보고 마스크 구조가 단순하다고 설명했는데, 코드를 보니 **U자 마스크를 만들려는 구조는 이미 들어가 있습니다.**

문제는 마스크의 유무보다 **마스크와 중앙 턱판의 형태가 화면에서 명확하게 분리되어 보이느냐**에 가깝습니다.

### 권장 수정

마스크의 U자 형태는 유지하면서:

1. **좌우 볼 장갑**과 **중앙 턱판**의 역할을 명확히 분리
2. 중앙 턱판은 현재처럼 기존 표면을 그대로 따라가기보다, 별도의 간결한 판 형태로 설계
3. 턱판의 테두리는 모든 경계에 복잡하게 둘러치기보다, 잘 보이는 상단과 좌우 경계 위주로 단순화
4. 측면으로 감기는 U자 마스크는 유지하되, 내부 구조와 명도 차이를 주기

정면에서 아래처럼 읽히는 것이 목표입니다.

```text
  노란 좌우 장갑
     청록 바이저
  ┏ 어두운 경계 ┓
  ┃ 회색 중앙판 ┃
  ┗━━ U자 마스크 ┛
```

# 5. 이마판이 평평하게 보이는 이유

현재 흰색 이마판은 정면 다각형으로 지정됩니다.

```python
WHITE_F = [
    (253, 163), (301, 163),
    (301, 199), (292, 201),
    (277, 204), (262, 201),
    (253, 199)
]
```

그리고 색상을 정할 때:

```python
front_c = np.where(
    F("vis"), 6,
    np.where(F("mask"), 8,
        np.where(F("vent"), 3,
            np.where(F("white"), 2, 1))))
```

흰색 판은 주로 **앞면에 색을 부여하는 영역**입니다. 별도의 두꺼운 판으로 모델링하는 처리는 이 코드에서 명확하게 보이지 않습니다.

더구나 윗면은:

```python
top_c = np.ones(shp, np.uint8)
```

로 전부 노란색입니다. 주석에도 윗면의 흰 띠를 뺐다고 되어 있어요.

### 시각적으로 나타나는 결과

- 흰색이 정면에 붙은 사각형처럼 보임
- 머리 위에서 흰색 중앙판이 내려온다는 느낌이 약함
- 노란 장갑과 흰색 이마판의 경계가 색상 차이에 주로 의존함

### 권장 수정

원본과 더 닮게 하려면:

- 흰판을 단순 색상 영역이 아니라 **두께가 있는 중앙 장갑**으로 취급
- 흰판 위쪽 일부가 머리 윗면으로 이어지도록 시험
- 흰판 양옆에 노란 장갑이 약간 겹치거나 어두운 틈이 생기도록 조정
- 중앙 통풍구는 작은 검은 점보다는 **가로 홈**으로 읽히게 설계

다만 윗면의 흰 띠를 이전에 의도적으로 제거한 것으로 보이므로, 무조건 복원하기보다는 **짧은 흰색 상단 장갑을 넣은 안과 없는 안을 비교**하는 것이 좋겠습니다.

# 6. 측면이 허전한 이유: `VISOR_S`가 실제 색상 처리에서 빠짐

코드에는 측면 바이저 영역이 정의되어 있습니다.

```python
VISOR_S = [
    (616, 184), (632, 182), (652, 186),
    (656, 200), (646, 210), (626, 208),
    (618, 198)
]
```

하지만 현재 측면 색상 결정에서는 사용하지 않습니다.

```python
side_c = np.where(
    S("nose"), 2,
    np.where(S("masks"), 8, 1)
)
# r5: 옆 바이저 잔재 뺌
```

즉, `VISOR_S`는 영역 목록에는 들어가지만, 현재 코드에서는 측면 청록색을 칠하는 데 사용되지 않습니다. 주석을 보면 의도적으로 측면의 바이저 잔재를 제거한 것으로 보입니다.

### 이것이 의미하는 것

정면 바이저는 별도로 존재하지만, **측면을 따라 자연스럽게 이어지는 바이저 구조는 제한적**일 수 있습니다. 그래서 3/4나 측면에서:

- 정면의 발광 띠가 갑자기 끝나 보이거나
- 측면은 노란 껍질과 회색 마스크 사이가 단조롭거나
- 바이저보다 귀의 밝은 원이 더 눈에 띄는

현상이 나타날 수 있습니다.

### 수정할 때 주의

`S("viss")`를 그대로 다시 켜는 것만으로 해결하려 하면 예전에 제거한 **청록색 잔재**가 다시 생길 수 있습니다.

대신:

1. 정면 바이저의 좌우 끝을 기준으로
2. 측면에 짧게 이어지는 별도 영역을 만들고
3. 그 주변을 어두운 프레임으로 감싸고
4. 정면·측면·3/4에서 연결이 자연스러운지 확인

하는 편이 안전합니다.

# 7. 귀 원반: 크기와 발광을 따로 조절할 필요가 있음

현재 귀 원반은 다음처럼 만들어집니다.

```python
H.add(
    fv.cyl(G, "x", (ey, ez), er,
           rng=(sg * (xm - 3), sg * (xm + 2))),
    3
)

H.groove(
    fv.cyl(G, "x", (ey, ez), er * 0.5,
           rng=(sg * (xm + 1), sg * (xm + 3))),
    6
)
```

구조상:

- 바깥쪽은 색상 `3`의 원반
- 가운데는 반지름 `er * 0.5`의 청록색 영역

입니다.

이미지에서는 청록색 중심이 꽤 강한 포인트로 보입니다. 원본 쪽은 밝은 중심 자체도 있지만, **주변의 검은 기계 구조와 노란 측면 장갑**이 함께 중요합니다.

### 권장 수정

- 원반 자체를 무조건 없애기보다, **청록 중심 크기와 밝기부터 별도 조정**
- `er * 0.5`를 예를 들어 `0.35~0.45` 범위에서 비교
- 외곽의 검은 원반은 유지하거나 더 잘 보이게 하고
- 일부를 노란 측면 장갑으로 감싸서 ‘붙여 놓은 큰 귀’보다 ‘장갑 속 회전 부품’처럼 만들기

이 수치는 시작점일 뿐입니다. ×1.0에서는 1복셀 차이의 영향이 커서 실제로 렌더링하며 고르는 게 좋습니다.

# 8. 정면·측면 색이 만나는 부분의 우선순위

현재 표면 색상은 대략 다음 순서로 덮어씁니다.

```python
col = np.where(fc["side"], side_c, col)
col = np.where(fc["top"], top_c, col)
col = np.where(fc["front"], front_c, col)
```

즉, 한 복셀이 측면이면서 윗면이거나 정면이기도 할 때는 **나중에 적용한 색이 우선**합니다. 정면 색이 측면 색보다 우선하는 구조입니다.

복셀 모서리에서는 한 칸이 동시에 여러 방향의 표면이 되는 일이 흔합니다. 따라서:

- 흰색 이마판의 가장자리
- 노란색 장갑과 회색 마스크의 경계
- 측면 장갑의 모서리

등에서 의도와 다른 색이 나타날 수 있습니다.

실제로 작은 노랑·흰색 얼룩을 정리하는 후처리도 이미 들어가 있습니다.

```python
# 작은 얼룩 정리
for _ in range(2):
    ...
```

이 후처리는 유용하지만, **어떤 부품이 어떤 표면을 소유하는지**를 명확히 정의하는 것보다 보정에 가까운 방법입니다.

### 개선 방향

나중에 구조를 정리한다면 색상을 방향별로 계속 덮기보다:

- `forehead_plate`
- `side_armor`
- `mask`
- `visor_frame`

같은 **부품별 마스크를 우선 정의**하고, 각 부품의 경계와 색을 결정하는 편이 예측하기 쉽습니다.

# 9. `s=1.0`과 `s=1.3`은 단순 확대가 아님

코드에는:

```python
k = 0.319 * s
```

가 있고, 이 값이 이미지 좌표와 복셀 좌표를 변환하는 데 사용됩니다. 귀 크기와 목 반지름에도 `s`가 적용됩니다.

하지만 모든 값이 같은 방식으로 확대되는 것은 아닙니다. 예를 들어:

- 부품을 담는 초기 범위는 상당 부분 고정
- 목의 시작 높이 `212`는 고정
- 마스크 돌출 `h=2`는 고정
- 바이저를 파내는 횟수도 `2`로 고정

따라서 `×1.3`은 **머리 전체를 균일하게 1.3배 확대한 결과와는 다릅니다.** 큰 형태와 상대적인 디테일 두께가 달라질 수 있어요.

특히 ×1.0에서 2복셀 돌출은 비율상 더 두드러져 보일 수 있습니다.

### 실무적으로는

두 크기를 동시에 계속 손보기보다:

1. 우선 **×1.0 형태를 확정**
2. 돌출 깊이와 프레임 두께를 파라미터화
3. 그다음 ×1.3에서도 동일한 인상인지 확인

하는 순서를 추천합니다.
